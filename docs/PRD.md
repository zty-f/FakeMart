# 假装购 FakeMart 虚拟购物平台 PRD

版本：v0.4  
日期：2026-07-07  
阶段：产品规划 / 技术选型

项目英文名：FakeMart  
项目中文名：假装购

## 1. 项目背景

假装购（FakeMart）是一个首发面向中国大陆市场的移动端小程序、Web 和 App 虚拟购物平台。产品复刻真实购物和外卖的关键流程，包括浏览、搜索、加购、下单、虚拟支付、物流/配送进度、订单回看和消费统计，但不发生真实交易、不实际扣款、不真实配送。

产品目标不是做一个完整电商平台，而是做一个轻量、可信、可追踪的“虚拟消费模拟器”。用户可以在接近真实的购物体验中释放购买冲动，同时看到自己因为没有真实购买而“省下的钱”。运营方可以通过后台查看用户行为、活跃度、模拟订单、品类偏好和项目运行情况。

## 2. 产品定位

### 2.1 一句话定位

假装购是一个覆盖综合购物和外卖场景的虚拟购物小程序/网站/App，帮助用户模拟消费、追踪虚拟订单，并统计自己省下的钱。

### 2.2 命名规范

- 中文产品名：假装购。
- 英文产品名 / 工程代号：FakeMart。
- 用户可见场景优先使用中文名“假装购”。
- 代码仓库、包名、数据库命名和英文发布材料可使用 FakeMart。
- 对外介绍可使用“假装购 FakeMart”作为完整名称。

### 2.3 核心价值

- 对用户：提供接近真实但无真实花费的购物体验，降低冲动消费，沉淀“省钱成就感”。
- 对运营者：完整记录用户路径、品类偏好、模拟下单行为和活跃趋势，方便后续做内容、活动和增长分析。
- 对产品：用相对轻量的功能替代真实电商的复杂履约、支付、售后和商家体系，保持体验聚焦。

### 2.4 产品边界

假装购（FakeMart）明确不是：

- 真实电商平台。
- 真实外卖平台。
- 真实支付、真实物流或真实商家撮合系统。
- 真实品牌/商标/图片复刻平台。

假装购必须在注册、下单、订单详情、物流页等关键位置明确提示“虚拟购物 / 模拟订单 / 不会真实发货或配送”。

## 3. 目标用户

### 3.1 C 端用户

- 容易冲动购物，希望通过模拟下单缓冲消费欲望的人。
- 喜欢逛电商、外卖软件，但并不一定真的想消费的人。
- 希望记录自己“少花了多少钱”的用户。
- 希望用轻松方式做预算和消费反思的用户。

### 3.2 运营/管理用户

- 项目运营者：关注 DAU、WAU、留存、下单模拟次数、品类偏好、用户活跃度。
- 内容运营者：维护虚拟商品、虚拟商家、活动、推荐位和价格策略。
- 产品分析者：查看漏斗、行为路径、模拟订单状态、用户反馈。

## 4. 产品目标与指标

### 4.1 MVP 目标

- 用户能完成从浏览商品到虚拟下单、查看模拟物流、查看省钱统计的完整闭环。
- 所有关键行为都有事件记录。
- 运营后台能查看核心数据和订单模拟记录。
- 同一套业务代码优先支持微信小程序和 H5，后续扩展 App。

### 4.2 核心指标

- 活跃：DAU、WAU、MAU、日均会话数、平均访问时长。
- 转化：浏览商品人数、加购人数、模拟下单人数、下单转化率。
- 省钱：模拟下单省钱、浏览未买机会金额、加购未结算机会金额、综合省钱估算、按品类统计、日/周/月趋势。
- 留存：次日留存、7 日留存、30 日留存。
- 行为：搜索次数、品类点击、商品点击、外卖/综合购物占比、物流页查看率。
- 内容：热门商品、热门品类、热门虚拟商家、低互动商品。

## 5. 产品原则

- 真实感只服务于模拟体验，不制造真实交易误解。
- 流程要像购物，但功能不能像真实电商一样过重。
- 所有行为可追踪，所有模拟订单可回放。
- 尽量少收集真实敏感信息，默认使用虚拟地址和虚拟身份信息。
- 商品、品牌、店铺、骑手、物流公司默认使用虚构内容，避免侵权和误导。
- 首版先做闭环，不追求复杂推荐算法、复杂优惠券、复杂售后。

## 6. 端与平台范围

### 6.1 首发端

- 微信小程序：主入口，适合移动端传播和轻量使用。
- H5 Web：适合分享、SEO 内容页、桌面访问和快速测试。
- 管理后台 Web：运营与数据查看使用。
- 首发市场：中国大陆。

### 6.2 后续端

- iOS / Android App：在小程序和 H5 验证后发布。
- 其他小程序平台：支付宝、抖音、百度、京东等，视中国大陆用户来源扩展。

### 6.3 跨端策略

采用一套核心业务代码，多端适配：

- 通用层：商品、购物车、订单、物流模拟、行为埋点、统计口径。
- 平台层：微信授权、账号密码登录、分享、订阅消息、支付模拟 UI、地图能力、推送能力。
- 视觉层：保持统一设计语言，但允许小程序、H5、App 在交互细节上做差异适配。

## 7. 功能范围

### 7.1 用户端：首页

首页承担快速进入购物欲望场景的作用。

核心模块：

- 搜索入口。
- 顶部快捷分类。
- 推荐商品流。
- 外卖 Tab 状态提示或快捷入口。
- 今日省钱提示。
- 最近模拟订单状态。
- 活动位，例如“今日不买挑战”“虚拟大促”“深夜外卖模拟”。

MVP 要求：

- 首页商品可配置。
- 商品点击、曝光、分类点击全部埋点。
- 首页不做复杂内容流算法，先使用运营配置 + 简单热度排序。

### 7.2 用户端：商品分类

首版建议分类：

- 数码电器。
- 家居日用。
- 美妆个护。
- 服饰鞋包。
- 食品饮料。
- 图书文娱。
- 运动户外。

外卖不作为综合购物普通分类，首版使用独立底部 Tab 承载。

功能要求：

- 分类页支持二级分类。
- 支持价格区间、热度、上新、虚拟折扣排序。
- 每个分类记录浏览、点击、加购、模拟下单金额。

### 7.3 用户端：搜索

功能要求：

- 搜索商品、店铺/餐厅、分类。
- 支持搜索建议词。
- 支持热门搜索。
- 支持搜索历史。
- 搜索结果支持筛选和排序。

埋点要求：

- 搜索提交。
- 搜索词。
- 搜索结果数量。
- 点击结果位置。
- 无结果搜索词。

### 7.4 用户端：商品详情

商品详情需要提供足够真实的购买氛围，但不引入复杂真实电商负担。

核心内容：

- 商品图。
- 商品图 MVP 阶段必须来自授权素材库，并保留素材来源和授权范围；后续可增加自有素材或其他明确授权素材。
- 商品名。
- 虚拟价格。
- 虚拟划线价。
- 分类和标签。
- 简短描述。
- 虚拟库存。
- 虚拟销量。
- 模拟配送时效。
- “加入购物车”。
- “立即模拟下单”。

可选内容：

- 虚拟评价。
- 相似商品。
- 价格波动提示。
- “这次不买可省下 X 元”。

### 7.5 用户端：外卖场景

外卖作为独立底部 Tab，不与综合购物混在同一个一级入口里，但复用商品、商家、订单和配送模型。

入口要求：

- 底部导航提供独立“外卖”Tab。
- 首页可展示外卖状态提示或活动入口，但主入口仍归属于外卖 Tab。
- 外卖订单、外卖省钱、外卖配送可在统计页和订单页按类型筛选。

核心内容：

- 虚拟餐厅列表。
- 餐厅详情。
- 菜品列表。
- 配送费模拟。
- 起送价模拟。
- 餐品规格。
- 预计送达时间。
- 骑手/路线模拟。

外卖订单状态：

- 已创建。
- 商家已接单。
- 制作中。
- 骑手已接单。
- 骑手已取餐。
- 即将送达。
- 模拟完成。

注意：

- 不默认做热量、体重、身体评价等敏感方向。
- 如果后续加入饮食统计，应以用户自主设置为前提，避免制造压力型体验。

### 7.6 用户端：购物车

功能要求：

- 添加商品。
- 修改数量。
- 删除商品。
- 按店铺/类型分组。
- 展示本次模拟下单总额。
- 展示“如果不买，本次可省 X 元”。

限制：

- 不做真实库存锁定。
- 不做真实优惠券结算。
- 可做轻量虚拟优惠，例如虚拟满减、虚拟会员价。

### 7.7 用户端：虚拟结算

虚拟结算页是产品的关键识别点，必须避免误导为真实交易。

核心内容：

- 商品清单。
- 虚拟收货地址。
- 虚拟配送方式。
- 虚拟支付方式。
- 本次模拟金额。
- 本次省下金额。
- 确认按钮文案建议：“确认模拟下单”。

提示要求：

- 明确提示“不扣款、不发货、不配送”。
- 不接入真实支付。
- 不要求真实详细地址。
- 可提供“虚拟地址簿”，例如“家附近”“公司附近”“学校附近”。

### 7.8 用户端：订单

订单模块要完整可追踪。

核心功能：

- 订单列表。
- 订单详情。
- 订单状态时间线。
- 订单商品明细。
- 虚拟支付信息。
- 配送/物流模拟信息。
- 再来一单。
- 取消模拟订单。

综合购物订单状态：

- 已创建。
- 已虚拟支付。
- 仓库处理中。
- 已打包。
- 已出库。
- 运输中。
- 派送中。
- 模拟完成。

订单时间线要求：

- 每次状态变更生成一条不可覆盖的 order_status_events 记录。
- 记录状态、发生时间、模拟说明、触发来源、任务 ID。
- 用户查看订单和物流页也需要记录行为事件。

### 7.9 用户端：物流/配送模拟

物流模拟不需要真实接入快递公司，但要有可信的时间线。

综合购物模拟：

- 根据品类、虚拟仓库、用户虚拟地址生成预计时间。
- 通过异步任务推进状态。
- 可配置快慢节奏，例如“极速达”“普通配送”“延迟配送”。

外卖配送模拟：

- 根据餐厅距离、制作时长、配送时长生成状态。
- 可展示简化地图或路线动画，但不采集真实精确位置。
- 骑手、餐厅、路线均为虚构。

运营要求：

- 后台可查看某个订单的完整状态流。
- 可重放某个订单的模拟过程。
- 可手动触发某个订单进入下一状态，用于测试和运营演示。

### 7.10 用户端：省钱统计

这是产品的核心留存模块。

核心指标：

- 累计省下金额。
- 今日省下金额。
- 本周省下金额。
- 本月省下金额。
- 模拟下单省下金额。
- 浏览未买机会金额。
- 加购未结算机会金额。
- 按品类省下金额。
- 按外卖/综合购物省下金额。
- 模拟下单次数。
- 平均单次省下金额。

视图：

- 总览页。
- 分类排行。
- 时间趋势。
- 订单明细。
- 忍住没买明细。
- 浏览未下单商品排行。
- “本月原本可能花掉的钱”。

统计口径：

- 模拟下单省钱：以已提交且未取消的模拟订单金额计入，是最稳定的主口径。
- 浏览未买机会金额：用户浏览商品详情后，在当前会话或统计周期内没有加购、没有模拟下单时计入机会金额。
- 加购未结算机会金额：用户加入购物车后，在当前会话或统计周期内没有提交模拟订单时计入机会金额。
- 综合省钱估算：模拟下单省钱 + 去重后的浏览未买机会金额 + 去重后的加购未结算机会金额。
- 被取消的模拟订单可单独统计，不计入默认模拟下单省钱。
- 重复下单计入多次；浏览未买和加购未结算按“用户 + 商品/SKU + 自然日”去重，避免金额被无限放大。
- 用户端总览同时展示“确定省下”和“估算省下”，后台可切换不同统计口径。

### 7.11 用户端：登录与账户

首版不采集手机号，采用微信授权和用户名密码账户体系。

小程序登录：

- 微信小程序使用微信授权/静默登录创建用户身份。
- 用户可选择绑定用户名和密码，方便后续在 H5、App 或其他端登录同一账户。
- 不要求手机号登录，不把手机号作为账户主标识。

H5 / App 登录：

- 使用用户名 + 密码登录。
- 支持注册用户名密码账户。
- 支持绑定已有微信小程序账户。
- 支持找回密码，MVP 可先使用邮箱或后台重置方案；如果不接邮箱，需提供安全问题或管理员重置流程。

账户要求：

- 用户名唯一。
- 密码服务端只保存哈希，不保存明文。
- 同一用户可拥有多个登录方式，例如微信 openid + 用户名密码。
- 注销账户时需要解除登录绑定，并清理或匿名化个人数据。

## 8. 用户行为记录系统

### 8.1 设计原则

- 所有关键用户路径都要可追踪。
- 行为事件采用统一 schema。
- 事件数据尽量不可变，后续通过聚合表生成统计。
- 采集前要有隐私说明。
- 避免采集不必要的真实敏感信息。

### 8.2 事件通用字段

- event_id：事件 ID。
- event_name：事件名称。
- user_id：用户 ID，可为空。
- anonymous_id：匿名设备/访客 ID。
- session_id：会话 ID。
- platform：wechat_mp、h5、ios、android、admin。
- page_path：页面路径。
- referrer：来源页面。
- occurred_at：客户端发生时间。
- received_at：服务端接收时间。
- app_version：应用版本。
- device_info：设备摘要。
- network_type：网络类型。
- experiment_id：实验 ID，可为空。
- properties：事件扩展字段。

### 8.3 核心事件清单

- app_open：打开应用。
- page_view：页面访问。
- search_submit：提交搜索。
- search_result_click：点击搜索结果。
- category_view：查看分类。
- product_impression：商品曝光。
- product_click：商品点击。
- product_view：商品详情访问。
- add_to_cart：加入购物车。
- remove_from_cart：移出购物车。
- checkout_start：开始结算。
- virtual_payment_select：选择虚拟支付方式。
- simulate_order_submit：提交模拟订单。
- order_created：订单创建成功。
- order_status_changed：订单状态变化。
- order_detail_view：查看订单详情。
- logistics_view：查看物流。
- savings_view：查看省钱统计。
- savings_opportunity_created：生成浏览未买或加购未结算机会。

### 8.4 行为链路

- 用户。
- 会话。

- 商品点击。
- 加购。
- 结算。

- 用户。
- 会话。
- 商品曝光。
- 商品详情访问。

- 会话结束或统计任务。

- 是否后来转化为模拟订单。

## 10. 物流模拟规则

### 10.1 规则类型

- 固定时间规则：创建后 N 分钟进入下一状态。
- 随机时间规则：在一个时间区间内随机推进。
- 品类规则：数码、家居、外卖等不同节奏。
- 用户场景规则：深夜外卖、周末购物、虚拟大促等。
- 运营规则：后台指定某类订单更快/更慢。

### 10.2 状态推进

状态推进由后端任务队列负责。

流程：

1. 用户提交模拟订单。
2. 服务端创建订单和第一条状态事件。
3. 物流模拟引擎生成后续状态计划。
4. 任务队列按计划推进状态。
5. 每次推进写入 order_status_events。
6. 用户端通过轮询或推送获得状态更新。

### 10.3 异常模拟

可配置少量虚拟异常，增加真实感：

- 虚拟仓库繁忙。
- 骑手稍微绕路。
- 天气原因延迟。
- 商品正在调拨。

注意：异常文案必须保持轻量，避免让用户误以为有真实损失。

## 11. 非功能需求

### 11.1 性能

- 首页首屏在常规 4G 网络下尽量 2 秒内可交互。
- 商品列表分页加载。
- 图片使用 CDN 和多尺寸裁剪。
- 埋点批量上报，避免影响页面交互。

### 11.2 稳定性

- 订单创建和状态事件写入必须事务化。
- 状态推进任务需要幂等。
- 埋点失败不能影响主流程。
- 后台操作需要审计日志。

### 11.3 安全

- 用户端和后台权限隔离。
- MVP 后台使用单管理员或少量固定管理员账号，不做复杂多人权限。
- 后台 RBAC 作为后续预留能力，不进入 MVP 必做范围。
- API 鉴权。
- 管理操作记录日志。
- 不存储真实支付凭证。
- 不存储手机号。
- 用户密码必须加盐哈希存储。

### 11.4 隐私

- 默认不采集真实详细地址。
- 默认不采集真实精确定位。
- 默认不采集手机号。
- 行为记录需要在隐私政策中说明。
- 支持注销、清空历史、数据导出。
- 数据保留周期可配置。

### 11.5 可观测性

- API 日志。
- 错误追踪。
- 慢请求监控。
- 任务队列监控。
- 埋点接收成功率。
- 订单状态推进失败告警。

## 12. 技术方案

### 12.1 推荐方案

推荐使用 TypeScript 全栈 monorepo：

- 用户端：Taro + React + TypeScript。
- 小程序 UI：NutUI React / Taro 生态组件，结合自定义业务组件。
- H5：同一 Taro 项目输出 H5。
- App：后续通过 Taro React Native 或单独 React Native/Expo 复用业务包。
- 管理后台：React + Vite + TypeScript + Ant Design 或 Arco Design。
- 后端：NestJS 或 Fastify + TypeScript。
- 数据库：MySQL 8.x。
- 缓存/队列：Redis + BullMQ。
- 文件存储：S3 兼容对象存储或云厂商 OSS/COS。
- 图表：ECharts 或 VisActor。
- 包管理：pnpm workspace。
- ORM：Prisma 或 Drizzle。
- API：REST 起步，后台复杂查询可补充 RPC/GraphQL。

### 12.2 为什么推荐 Taro

- 适合一套代码发布到微信小程序、H5，并可拓展更多小程序平台。
- React + TypeScript 生态成熟，利于多人协作和长期维护。
- 业务逻辑、埋点、状态管理和接口类型可以跨端共享。
- 项目定位接近电商，Taro 和 NutUI 生态对小程序/电商组件更友好。

### 12.3 备选方案：uni-app

如果开发团队更熟悉 Vue，或更看重国内小程序 + App 的成熟工程链路，可以选择 uni-app：

- 用户端：uni-app + Vue 3 + TypeScript。
- UI：uView Plus / uni-ui。
- App：uni-app 原生打包链路。
- 后台和后端不变。

取舍：

- Taro 更适合 React 技术栈和复杂前端工程治理。
- uni-app 更适合 Vue 团队和国内多端快速发布。
- 两者都无法做到 100% 无差异复用，登录、订阅消息、分享、地图、发布审核都需要平台适配层。

### 12.4 建议项目结构

```text
FakeMart/
  apps/
    client/        # Taro 用户端：小程序 + H5
    admin/         # 运营后台 Web
    api/           # 后端 API
  packages/
    shared/        # 共享类型、常量、工具
    event-schema/  # 埋点事件定义
    sim-engine/    # 订单/物流模拟规则
    ui/            # 可复用业务组件
  docs/
    PRD.md
```

### 12.5 服务端架构

核心模块：

- AuthModule：微信授权登录、用户名密码登录、账户绑定、匿名会话。
- CatalogModule：分类、商品、商家。
- CartModule：购物车。
- OrderModule：订单创建、订单查询。
- SimulationModule：物流/配送状态推进。
- EventModule：行为事件接收和校验。
- AnalyticsModule：模拟下单省钱、浏览未买机会金额、加购未结算机会金额、活跃统计聚合。
- AdminModule：后台管理。

数据链路：

1. 用户端产生行为事件。
2. 事件批量发送到 Event API。
3. Event API 校验 schema 后写入 user_behavior_events。
4. 定时任务根据商品浏览、加购、订单转化生成 savings_opportunity_records。
5. 定时任务将事件和省钱机会聚合为日统计、漏斗统计、品类统计。
6. 后台读取聚合表和明细表。

订单链路：

1. 用户提交模拟订单。
2. Order API 创建 orders、order_items、order_status_events。
3. SimulationModule 创建状态推进计划。
4. BullMQ 定时任务推进状态。
5. 每次推进写入状态事件并更新 orders.status。
6. 用户端展示状态时间线。

### 12.6 数据分析方案

MVP 阶段：

- MySQL 存储业务数据和明细事件。
- 定时任务生成日级聚合表。
- 后台直接查询聚合表。
- 高频明细事件表按时间分区或按月归档。
- 金额字段统一使用“分”为单位的整数，避免浮点误差。
- JSON 字段只存扩展属性，常用筛选字段需要拆成独立列并建立索引。

增长阶段：

- 事件量上来后引入 ClickHouse。
- 行为分析可接入自建 PostHog 或类似系统。
- 保留自有事件 schema，避免完全依赖第三方分析平台。

## 18. 关键风险

### 18.1 误导用户风险

风险：用户误以为是真实购物平台。

应对：

- 关键页面明确提示虚拟购物。
- 按钮使用“模拟下单”。
- 状态使用“已虚拟支付”“模拟配送中”。
- 不接真实支付。

### 18.2 侵权风险

风险：使用真实品牌、真实商品图、真实商家信息导致侵权。

应对：

- 商品、商家、物流公司、骑手均使用虚构信息。
- 商品图、餐品图和活动图优先使用授权素材库。
- 每张素材记录来源、授权类型、使用范围和授权有效期。
- 不使用真实平台 UI、Logo 和商标。

### 18.3 数据隐私风险

风险：行为记录过细、地址定位采集不当。

应对：

- 默认匿名/虚拟地址。
- 用户可清空历史、注销、导出数据。
- 明示行为数据用途。
- 后台限制明细数据访问权限。

### 18.4 跨端复用风险

风险：一套代码在小程序、H5、App 体验不一致。

应对：

- 业务逻辑抽到 packages。
- 平台能力做 adapter。
- 首发只承诺微信小程序 + H5。
- App 在 MVP 验证后再进入。

### 18.5 数据量增长风险

风险：行为事件增长后 MySQL 明细表查询变慢。

应对：

- MVP 使用聚合表。
- 事件表按时间分区。
- 明细事件按月归档，后台默认查询聚合数据。
- 增长后引入 ClickHouse。

## 19. 已确认决策

- 首发市场：中国大陆。
- 小程序登录：微信授权/静默登录为主。
- H5 / App 登录：用户名 + 密码。
- 账户绑定：微信账户可绑定用户名密码，跨端共享同一用户资产。
- 手机号：首版不采集，不作为登录方式。
- 商品图片：MVP 使用授权素材库，并记录素材来源和授权范围。
- 外卖入口：首版作为独立底部 Tab。
- 运营后台权限：MVP 暂不做多人权限，使用单管理员或少量固定管理员账号。
- 省钱统计：模拟下单、浏览未买、加购未结算都统计，但分不同口径展示。
